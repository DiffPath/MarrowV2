# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The **standardized layout shell** for a family of pathology report builders —
single-page, client-side web apps. It is a deliberate fresh start: the shared shell
(nav drawer, header, tabs, panels, toast) is present and working, and each template
(bone marrow, liver, placenta, ...) is defined by a small config file. All report
content and logic has been stripped out and is to be rebuilt; bone marrow is the
primary template being rebuilt here.

The previous full version lives in `../Marrow/` and is preserved untouched. Treat it as
a reference to copy *from*, never as something to edit as part of work here.

Author: Michael Moravek, MD. Not for clinical use.

## Running & developing

- **No build step, no bundler, no package manager, no tests.** Pure static HTML/CSS/vanilla JS.
- **`images/rbc/` is the only binary content** — vendored photomicrographs for the reference
  section's red cell atlas, ~3MB. Vendored and never hotlinked: the app must work from `file://`
  offline and must make no outbound request from a screen that has patient data on it. The
  FontAwesome kit in the `<head>` is the one remaining exception and predates this.
- To run: open `Marrow.html` (or `Liver.html`) directly in a browser (or serve the folder with any
  static server, e.g. `python -m http.server`, if you need a real origin for clipboard APIs).
- The only external dependency is a FontAwesome kit loaded from a CDN (`<script>` in the `<head>`).
- "Test" by loading the page and clicking through the tabs; check the browser console.

`docs/who/` now has a second consumer: the reference section (`MarrowRefData.js`)

against it, then clear it. Three flags have been cleared that way and **every one was
covering a real error**, including a megakaryocyte count wrong by fivefold; five remain, all
because no criteria box has been pasted for them. Provenance for the *transcribed* topics is
a `//` comment above each one, deliberately not rendered.

an `unverified` flag** — those are the only two honest states, and shipping a number with
neither is what produced that fivefold error. See [docs/reference.md](docs/reference.md).

Each family file holds **its own helpers above its own rules**, which is the property that makes the
split worth having. Three ordering constraints, all stated in `Marrow.html`: kernel first;
`MarrowDxMpn` before `MarrowDxMdsMpn` (the CMML rule reads `dxMpn` at load time, so the wrong order
is a `ReferenceError`, not a subtle bug); engine and panel after all six families.

**The Specimen tab's template selection is a prior on the ranking** (`dxWorkupBonus`,
`MarrowDxEngine.js`): the workup's family gets `DX_WORKUP_POINTS` and — the one exception to
"only case evidence lifts a candidate" — escapes `unassessed`, so choosing "Rule out plasma cell
neoplasm" on an otherwise blank form makes the differential exactly that family's three
candidates. Family-scoped on purpose: an MDS workup must not lift AML candidates across the
exact boundary the workup was opened to judge. `lymphoma` is mapped but has no rules yet.
The template type still emits no report text of its own.

**Report sections combine two specimens under one dynamic heading.** The aspirate section prints the
aspirate smear and the touch preparation together, and the core section does the same for the core
biopsy and the particle clot; the heading is emitted *inside* the combined fill, so an empty section
takes its heading down with it. There is no separate `touch` or `clot` registration.


Entry pages are identical copies except for one line: the `<script>` that loads their
config. A config defines the page title, drawer links, input tabs, copy buttons, and
settings tabs. **To spin up a new template**: duplicate an entry page, point its config
`<script>` at a new `<Name>Config.js`, and write that config. The entry pages also
contain the fixed chrome markup and the empty mount points (`#navLinks`, `#inputTabBar`,
`#inputBodies`, `#copyButtonBar`, `#settingTabBar`, `#settingBodies`) the shell fills at
runtime.

There are no ES modules. Files communicate through globals at script scope, so load
order matters: the config script must load before `Template.js` (both at the bottom of
`<body>`); content scripts load after `Template.js`.

**`MarrowForm.js` must load before `MarrowReport.js`.** Both bind a `change` listener to
`#inputPanel`, and listeners fire in the order they were added. The toggle-group handler has to
have cleared the rest of a group *before* `fillReport()` reads it — otherwise a click that swaps
two chips builds the report from the instant when both were checked. Nothing errors if you get
this wrong; the report is just briefly, silently wrong.


## Core architecture

### Config-driven shell
`Template.js` builds the template-specific chrome at page load from `templateConfig`
(defined in the page's config script, e.g. `MarrowConfig.js`). Each tab entry
`{ id, label, icon }` generates a tab element `#<id>Tab` and an empty panel body
`#<id>Panel`, following the id convention (`spec` → `#specTab` / `#specPanel`). If the
markup already contains a body with the conventional id, the shell uses it instead of
creating one. The first tab in each list starts selected. To add/rename/reorder tabs or
copy buttons: edit the config file only.

### Tab switching (the one convention to know)
Every clickable tab has class `headerTab` plus, **as its first class**, the name of its
tab *group*: `pageTab` (top-right icons), `templateTab` (left panel sub-tabs), or
`settingTab` (settings sub-tabs). The switcher reads `className.split(' ')[0]` to find
the group, hides every panel owned by that group, then shows the clicked tab's panel.
Groups therefore switch independently and nest without extra code.

`headerObject` in `Template.js` maps **tab id → panel id**. The `pageTab` entries are
declared statically (fixed shell chrome); `templateTab` and `settingTab` entries are
added at runtime by `buildTabs()` from the config.

Note the left input panel (`#inputPanel`) is not in `headerObject` and so stays visible
across page-tab switches — this matches the original app's behavior. **The reference
section depends on that property**: opening the book swaps the *report* panel for the
reference and leaves the form you were filling in exactly where it was, which is what makes
a quick link from a form row worth having. See [docs/reference.md](docs/reference.md).


## Cross-cutting contracts

Everything in this section applies to every tab. Anything that applies to only one has moved to
`docs/` — see the table above.

`registerReportSection({ id, fill, when?, heading? })` creates `#<id>Container` > `#<id>Div` inside
`#rightPanelFinal` in registration order. `fill()` is a pure DOM-reader returning an HTML string
(`''` hides its section). The optional `when: () => boolean` predicate is the hook for gating a
section on a specimen part (not currently used — see below).

**`heading`** is the bold line above a section (`Peripheral Blood Smear`). It renders *inside* the
container, which is what stops a heading ever outliving its section: `fillReport()` hides the
container whole, so an empty section takes its heading down with it. Omit it where a section
already says what it is — the specimen line IS the report's title, and the CBC and differential
tables carry their own captions.

`class="form"` on a control opts it into live re-render; the delegated listener on `#inputPanel`
calls `fillReport()`. Generated markup must keep `<input>`/`<label>` as adjacent siblings, since both
the §2 spacing cascade and the chip styling key on the `+` combinator.


Report HTML carries its Word styling **inline** — a stylesheet does not survive the clipboard, so
anything that must land in Epic/Word intact has to be on the element. Use **`REPORT_PARAGRAPH`**
(`MarrowReport.js`) for a body paragraph and **`REPORT_HEADING`** for a section heading; don't
retype the bytes. "Keep them byte-exact" is a rule you can only really keep with one copy, and they
had already been retyped in two tabs.

The spacing rule between the two: a body paragraph carries `margin-bottom: 8.0pt` (the space
*after* a section) and a heading carries `margin-top: 8.0pt; margin-bottom: 0` — so the gap sits
between sections and never between a heading and the text it heads.


### The `applySettings()` load-order trap
`MarrowSettings.js` calls `applySettings()` at **its own script scope**, which is long finished by
the time any later content script runs. So a `.setting` control rendered from a later file is
never restored from localStorage, and `getSetting()` reads the *control*, not storage — it would
silently return the markup default. Any later file that renders settings must re-run
`applySettings()` itself before anything reads them (it's idempotent). `MarrowSpec.js` only gets
away without this because its one setting lives in the misc panel, rendered before that call.

`MarrowBlood.js`'s bootstrap is the worked example, and its three lines are one sequence rather
than three statements: `renderSettings()` (the `.setting` controls must exist) → `applySettings()`
(storage restored into them) → `render()` (reads them back through the seam). Reorder it and the
pad silently drops to defaults for anyone with saved bindings.


## Conventions & gotchas

- The `.copyHeader` copy buttons are wired in **`MarrowReport.js`** (the section registry owns
  what each copies): Copy Final → `spec`, Copy Comment → `dxCommentSection`, Copy Clinical →
  `cbc`, and Copy Microscopic → **everything unclaimed**, derived from the registry so a new
  section is microscopic by default. Each copies whole visible containers as `text/html` +
  `text/plain` via the async clipboard API, falling back to the old app's synthesized-copy-event
  trick (which works from `file://`). `newMarrowBtn` clears the worksheet: confirm, then
  `location.reload()` — a fresh load is the canonical empty state and the app persists no case
  data, so there is no clear-list to keep complete. The old app's Epic HTML+RTF "Method 5" path
  for the final-diagnosis bullet is deliberately not ported until that line itself is rebuilt.

- When rebuilding, prefer data-driven UI over hard-coded markup: the original populated
  its dropdowns at runtime from data objects via `data-selectType` / `data-parentID`.
- Keep clinical/report strings exact — small wording, threshold, and punctuation changes
  are meaningful in this domain. This applies to **report output only**. On-screen labels are
  free to differ (and to be shortened) — the data tables keep `label` and `phrase` separate
  precisely so the UI can change without touching a report string.
  - **Shorten by dropping words, never by substituting symbols.** A label is read at a glance by
    someone whose eye is coming off a microscope, and a symbol standing in for a word is a second
    thing to decode: `Scattered + focal aggregates` was tried for the CD3/CD20 options and is out —
    `+` is not "and". Dropping a redundant word is fine where the row already supplies it
    (reticulin's options say `Mildly increased (MF-1)`, not `Mildly increased fibrosis`, because the
    row says Reticulin), and so is dropping a leading `Interstitially` **only** where nothing else
    in the list starts differently. Where options share a long prefix and differ at the END, keep
    them whole: a truncated `Interstitially scattered and focal …` loses the one word that
    distinguishes it, which is the opposite of what shortening is for.
  - The one sanctioned deviation is **whitespace**. The original concatenated sentence fragments
    that each assumed a neighbour, so skipping an optional word left a double space in the report
    ("shows  anemia", "There is  absolute eosinophilia"). Rebuilt sentences assemble from parts
    and join, so spacing holds whichever parts are present. Words, punctuation and thresholds are
    untouched — and `scratchpad/oracle.js`-style differential tests against the original's own
    `fillPB()` are how that claim is checked, normalizing whitespace on both sides.
- The UI layout, by contrast, is explicitly **not** bound to the original app. Prefer whatever
  is fastest to use; the previous version's arrangement is not a target.
- Classification nomenclature should name **both** WHO 5th edition (WHO-HAEM5) and
  ICC 2022 where they diverge.
- PHI must never be persisted. The original deliberately excluded the raw CBC paste box
  and raw pasted NGS text from its saved snapshots; preserve that rule in anything new.
  **The marker is `class="noSave"` on the control itself** (currently `#pbCBC`). No case-save
  code exists yet — when it lands, its capture *and* restore must both skip `.noSave`.
- The specimen checkboxes gate **only** the header string, not section visibility — unchecking
  "Core biopsy" will still emit core morphology prose, matching the original. This is a deferred
  clinical decision, not an oversight; `registerReportSection`'s `when` predicate is the hook if
  it changes.
- Template type emits no report text of its own, but it is no longer UI-guidance only: it is a
  prior on the Diagnosis ranking (`dxWorkupBonus` — see the Diagnosis section above). Read it via
  `currentTemplateType()` (radio group `name="templateType"`, values like `ruleOutMDS`).
